# v2.x Retrospective

> **Cycle**: v1.0.0 (2026-04-19) → v2.0.0 (2026-04-22)
> **Calendar**: 3 days
> **Commits**: 78 on `v2.x-prep`
> **Sprints**: S1 (self-play league) → S2 (reward simplification) → S3 (LSTM) → S4 (SAC) → S5 (Dreamer V3)
> **QA**: 5/5 sprint regression PASS at `f0290ac9`

## What went well

- **Parallel 3-team impl pattern landed cleanly.** Each sprint split into an AI track (model/algorithm code), a BE track (schema + WS plumbing + run-record threading), and an FE track (selector UI + chips + drill-down label). The three tracks merged into the sprint via `merge:` commits per the v1 refactor gate methodology. S1 alone shipped 22 commits across the three tracks with zero integration bugs after the hotfix (`88208f3c`, see below).
- **Watchdog improvements paid off.** The `training:update_start`/`update_end` explicit WS events landed in S1 and eliminated the heuristic "frame stall → overlay" guessing that had been ambiguous in v1. Designer wrote the overlay spec (`f02a9785`) first; FE implemented against it; AI added the BE emitters. Three contributors, one contract, no back-and-forth.
- **Boundary contract discipline.** Every sprint S2-S5 added exactly one Literal field to `training:start` + `run record` + `HyperparamForm`. Same three locations every time. This made rebase mechanics predictable: PM could tell which sprint conflicted with which.

## What hurt

- **S3, S4, S5 all conflicted on `trainer.py`.** Each sprint added a branch in the algorithm switch, and because they rebased in order (S2 → S3 → S4 → S5) not in parallel, each had to re-resolve the previous sprint's merge. Mitigation was to land the sprints one at a time and rebase the next against the merged result — workable but cost ~30 min per sprint.
- **Dreamer V3 VecEnv shape bug** (`19c7e45d`). The initial Dreamer merge shipped with `_collect_step` assuming `n_envs=1`; any multi-env run failed with a tensor shape mismatch in batch dim. Not caught by unit tests (which used `n_envs=1`) and not caught by the wm loss smoke test (`104575a5`, also `n_envs=1`). Only surfaced when the hyperparam form was driven with `n_envs>1`. Fix was trivial once located; the lesson is that smoke tests should exercise a realistic config, not the degenerate one.
- **TrainingServiceWrapper.start signature drift** (`88208f3c`). S1 added `training_mode` and `sampling` fields to the payload, but the service-wrapper facade didn't get its signature updated in the same commit. Backend accepted the WS message and silently dropped the two new fields until the hotfix. Caught by FE QA because the Opponent segmented control had no effect.

## Lessons learned

1. **Interface-contract memory.** Every time a WS payload schema changes, the *entire* chain must update in one atomic commit: Pydantic model → service wrapper → run-record persistence → FE type → FE usage. The S1 hotfix proves the facade layer is easy to forget. Going forward, adding a new field to `training:start` requires a checklist: five call sites grep-able by field name before landing. Candidate for a pre-commit grep guard.
2. **Periodic poll as a safety net.** Heuristic frame-stall detection for the updating overlay is the fallback the explicit WS events are supposed to obsolete. We kept it in v2 because removing safety nets before the replacement is field-tested is how we end up with "feature works in dev, silent in prod." Keep both for at least one major cycle.
3. **Smoke tests should default to realistic configs.** Dreamer passed all checks with `n_envs=1`; breaking at `n_envs>1` was a user-visible regression at QA time. New rule: smoke tests for multi-env algorithms run with at least `n_envs=2`. Applied retroactively to Dreamer (`104575a5` was updated post-hoc).

## Next major priorities (v3.x placeholder)

- **Mixed-algorithm Elo league.** Currently Dreamer V3 entries are tagged and isolated from PPO/SAC entries in the standings. A principled cross-algorithm rating (or an explicit separate pool per algo) is a v3 topic.
- **LSTM × SAC combination.** Explicitly deferred in S4 scope. Filling in the matrix cell is v3 work — SAC-Discrete with a recurrent head.
- **League-based curriculum.** Use the league Elo distribution to pick opponents at the student's skill level automatically, rather than the current uniform/elo-biased/champion tri-choice.
- **Reward `learned_shaped_v1` Stage 2.** v2 ships the selector but the actual IRL-learned shaping training pipeline is Stage 2 — next major.
- **Checkpoint migration across algorithms.** Current state: PPO↔SAC no; anything↔Dreamer no. Worth investigating whether a distillation-based migration (train a SAC student against a PPO teacher) makes sense for the league pool.
